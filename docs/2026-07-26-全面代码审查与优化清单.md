## 一、安全（12 条：高 4 / 中 6 / 低 2）

> **总评**：外围防护基线不错——pbkdf2 240k 加盐、登录锁定与限流、CSP 与 Cookie 硬化、`admin.py` 全部 42 条路由逐条挂了权限装饰器、SQL 全部参数化（无注入面）、`.env`/`users.db`/`.secret_key` 均已 gitignore、截图路由有防穿越。
> **但两处信任边界被击穿**：①用户上传的策略/因子经纯黑名单 AST 检查后直接 `exec_module` 进 Web 进程；②精心设计的实盘双开关被一个已提交进 git 的 JSON 架空。

### S-1 【高】用户策略 AST 黑名单可被 importlib 绕过 → 生产服务器进程级 RCE
`strategy_engine/strategy_manager.py:157-159`、执行点 `:661-671`

黑名单只有 `os/sys/subprocess/shutil/socket/requests/urllib/http/ftplib/smtplib/paramiko`，**不含 `importlib`/`pathlib`/`builtins`/`ctypes`/`pickle`**；且 `ast_check` 对函数调用只比对裸名字（`importlib.import_module` 的 attr 是 `import_module`，不在名单）。

完整攻击链：任意受邀用户 → `/api/strategies/save`（仅 `@require_auth`）存入 `import importlib; importlib.import_module("os").system(...)` → 点「激活」→ `scan_service.py:101` 调度器在 Web 进程内周期性 exec → 可读 `data/users.db`（全部用户密码哈希）、`.env`（tushare/AI key）、`data/.secret_key`（**伪造任意用户含 admin 的 session**）、篡改他人策略、反弹 shell。

无任何上层补位（`app_security` 的两个 `before_request` 只做 JSON 形状校验和反爬限流）。

**改法**：黑名单不可能穷尽，必须改「进程隔离 + 白名单」——①策略执行移到独立子进程（资源/时间上限），Linux 叠 seccomp/nsjail 或至少非特权用户 + 只读挂载；②AST 改白名单（只放行 pandas/numpy/math/statistics），禁止一切 `__` 开头的属性访问；③exec 时传裁剪过的 `__builtins__`；④补 importlib/pathlib/ctypes/dunder 逃逸用例（现有 `test_paper_broker.py:300-345` 只测了 os/subprocess/eval/exec 四个）。

### S-2 【高】`data/trade_settings.json` 被 git 跟踪且 `auto_confirm_order: true`，启动时无条件架空实盘双开关
`data/trade_settings.json` + `broker/ths_operator.py:110-146`

已亲自复核：`git ls-files` 命中该文件，`git show HEAD:data/trade_settings.json` 内容确为 `{"auto_confirm_order": true, "auto_cancel_unfilled": true, "auto_cancel_delay": 15.0}`。

`ths_operator.py:110-113` 先取 `config.AUTO_CONFIRM_ORDER`（双闸产物，默认 False），紧接着 `_load_trade_settings()` 用磁盘文件**无条件覆盖**，不做 AND 收敛、不看 `DRY_RUN`。落地点 `:584` `if self.auto_confirm_order:` → 自动点掉委托确认框 → 真成交。

`.gitignore` 里 `data/` 下 `ai_config.json`/`users.db`/`bridge_flags.json` 等运行态文件都逐条忽略了，**唯独漏了这一个**。于是 `deploy/server_update.sh` 的 `git pull` 会把「自动确认=开」分发到每台机器。

**改法**：①`git rm --cached ths_auto_trader/data/trade_settings.json` 并补进 .gitignore；②改成只能收紧不能放开：`self.auto_confirm_order = AUTO_CONFIRM_ORDER and bool(d[...])`；③启动日志打印最终生效值与来源。

### S-3 【高】7 条 `/api/mobile_ths/*` 零鉴权，未登录 GET 即可开启「自动确认下单」、切实盘、重启桥接
`web/bridge.py:764-811`

`profile(764)` / `connection(769)` / `confirm_mode(776)` / `account(783)` / `open_ths(797)` / `mode(802)` / `restart_bridge(809)` —— 全部无任何装饰器，且 `methods=["GET","POST"]`。同文件 `:816`/`:825` 的新版 `/api/bridge/mobile/*` 都带 `@require_bridge_or_auth`，**这组 legacy 是迁移遗漏**。

- `GET /api/mobile_ths/confirm_mode?mode=auto` → 写入 `tools/bridge_config.json` 持久化 → `mobile_ths_operator.py:1275-1278` 真点最终确认按钮
- `GET /api/mobile_ths/mode?mode=real` → 手机同花顺从模拟盘切实盘
- `GET /api/mobile_ths/restart_bridge` → 服务器上 kill + Popen 子进程

因为是 GET 且不需要 cookie，**任意恶意网页一个 `<img src="http://127.0.0.1:5001/api/mobile_ths/confirm_mode?mode=auto">` 就能远程打开自动下单闸门**，SameSite=Lax 完全挡不住。`main.py:260` 默认 bind `0.0.0.0`（同一 LAN 可直连），云端 nginx `location /api/` 全量转发。

**改法**：①7 条全加 `@require_bridge_or_auth`；②methods 收敛为 POST，去掉 `request.args` 取参；③`confirm_mode=auto`/`mode=live` 额外要求 root admin；④确认无调用方就直接删。

## 二、性能与稳定性（10 条：高 3 / 中 4 / 低 3）

> **总评**：架构是「单 gunicorn worker × 8 gthread + 进程内内存状态」，瓶颈高度集中。**本维度找到了 MEMORY 里记录的「云端选股返回 0、进程态坏死、重启即好」事故的完整机理**（见 P-2）。SQLite 侧（WAL、索引）做得相对到位，是亮点。

### P-1 【高】全市场扫描每只股票都全量重写 858KB `metadata.json` + 本地 CSV，且无锁
`analytics/data_manager.py:321-366`（merge_kline_cache）、`:1013-1023`（_load_meta/_save_meta）、热路径 `:455-514`

`get_kline_by_config` 在 `update_cache=True`（**签名默认值**，`strategy_manager._get_kline:408` → `data_gateway.get_daily_kline:120-128` 均用默认）下对每只股票**无条件**调用 `merge_kline_cache` —— 即使 df 本来就是本地缓存命中。而 merge 每次都：重读旧 CSV → concat → 整份重写 CSV → `_load_meta()` 解析 + `_save_meta()` 用 `indent=2` **全量重写整个 metadata.json**（实测 858,216 字节，`data/daily` 有 4386 个 CSV）。

一次 5000 股扫描 ≈ 4300×(读+写) 858KB JSON ≈ **7GB 无效 JSON I/O** + 4300 次 json.loads/dumps（GIL 内串行，直接抢占唯一 worker 的 CPU），`SCAN_INTERVAL=30s` 周期发生。`_save_meta` 用 `write_text` 非原子截断写且该路径**无任何锁**，并发扫描可致文件截断损坏——代码里已有「元数据文件损坏，回退空（将触发重新下载）」的自愈日志，印证发生过。

**改法**：①读路径与写缓存路径分离（本地缓存命中且无新增行则跳过 merge）；②元数据改进程内 dict + 脏标记，定时/批量结束后 `tempfile + os.replace` 原子落盘，写入加锁；③或迁到 SQLite（项目已有 WAL 库）。

### P-2 【高】★事故根因★ 单 worker×8 线程下 SSE 常驻占线程 + 多条同步慢路由 → 线程池耗尽全站假死
`deploy/gunicorn.conf.py:10-13`（`workers=1` / gthread / `threads=8` / `timeout=300`，注释自认「SSE 长连接不能独占唯一请求通道」）

- **常驻占线程**：`web/paper.py:242-247` 与 `web/ai_trader.py:273-279` 是两条 `while True: q.get(timeout=30)` 的 SSE 流，**每个连接永久占一个 gthread**
- **同步慢路由**：`web/strategies.py:153` 同步全市场选股（注释自述 2-3 分钟，**异步版 run_async 已存在于 :159 但同步版未下线**）、`web/misc.py:150` 同步回测（codes 长度无上限）、`web/factors.py:298-299` 请求内同步 build_panel 12 线程拉全市场、`web/data.py:188-192` 现场抓 akshare 板块
- 无 gevent/eventlet、无并发信号量

**每个浏览器标签占 1-2 个 SSE 线程，3-4 个标签 + 1 次同步选股即可耗尽 8 线程** → 所有后续请求（含 `/api/health`）排队至 300s 超时 → 外部表现为 access.log 全 200/50 字节、「选股返回 0」、必须重启进程 —— **与 MEMORY 记录的生产事故完全一致**。

**改法**：①下线同步版 `/api/strategies/run` 与同步回测分支，统一走已有的 `run_async`/`start_backtest_async`；②SSE 改 gevent/eventlet worker 或独立进程（或退回轮询），至少 `threads` 提到 32 并用 nginx 限制每用户 SSE 连接数；③所有出网调用设短超时 + 信号量限并发。

### P-3 【高】provider=tushare 时全市场扫描每股 1-2 次远程 HTTP，无任何缓存
`analytics/data_manager.py:479-480`、`analytics/tushare_provider.py`

`tushare_provider.py` **全文件无 lru_cache/_cache/TTL**；`_replay_request:115-138` 失败时顺序试 3 个 base_url、默认 `timeout=25s`；`_fetch_replay_kline_qfq:290-322` 每股实为 **2 次 HTTP**（daily + adj_factor）。`get_kline_by_config:479-480` 在 primary=tushare 时直连远程、**完全不查本地 CSV**。

而 `datasource_config.py:18-25` 的 `DEFAULT_CONFIG` 就是 `provider='tushare'/mode='replay'`，`_normalize:49-51` 还把旧 'current' 配置迁移成 tushare —— **这是默认配置，不是边缘情况**。一轮扫描 ≈ 5000+ 次外网 HTTP；代理降级时单股最坏 75s，扫描线程可挂起数小时。另 `:461` 每股重读一次 `datasource_config.json`（无 mtime 缓存）叠加 5000 次文件 I/O。

**改法**：①tushare_provider 加进程内 TTL 缓存；②扫描优先本地日线，仅对缺最新交易日的股票**按 trade_date 批量补拉**（`refresh_factor_daily_cache` 已有此模式，直接复用）；③`get_internal_config` 加 mtime 缓存。

### P-4 【中】TDX 行情客户端全局单连接 + 粗粒度锁，全市场扫描持锁 5-15 秒
`market/ths_quote.py:161`（`with self._lock:` 包住全部批次循环，`:253` 注释自述全市场 5-15 秒），`get_kline:270`/`get_finance_info:306`/`get_index_quotes:329`/`get_index_kline:351` 共用同一把锁，`get_client:499` 全局单例，**锁等待无超时**。
前端每次 `/api/paper` 持仓轮询都经 `trade_service._paper_live_prices:467-478` 调 `get_quotes` → 在锁上排队最长 15s+，且各占一个 gthread —— 与 P-2 叠加加速线程耗尽。
**改法**：建 2-4 条连接的小连接池按调用方分流；或降锁粒度到单批次 + 等待超时；全市场快照统一走已有 5 分钟 TTL 的 `_mkt_cache`。

### P-5 【中】回测引擎逐日对每股做布尔掩码查价：O(交易日×股票数×行数)
`strategy_engine/backtest.py:444`。250 交易日 × 4000 股 ≈ 200 万次整列比较（每次分配 800 元素布尔数组），单次全市场回测**纯浪费数分钟到数十分钟 CPU**（GIL 内），且与 Web 同进程。
**改法**：加载后 `df.set_index("date")`，预先 pivot 出 date×code 的 open/close 宽表（O(1) 取整日截面）；`_kline` 用 `index.searchsorted` 切片代替布尔掩码。

### P-6 【中】异步任务注册表全部无界增长，回测结果含全量曲线常驻内存
`backtest.py:45`（`_bt_tasks` 只写不删，全仓无 pop/clear/del，`:986` 存的 result 含完整 equity_curve/trades/logs）、`strategies.py:25`、`data_manager.py:59`、`data.py:23`

## 三、交易逻辑正确性（12 条：高 1 / 中 7 / 低 4）

> **总评**：骨架清晰——模拟盘有 per-user 锁与 SQLite 持久化、实盘信号队列有当日去重与隔日过期、T+1/整手/单笔金额护栏基本齐全，纯函数化的 sell_rules/order_sizing/daban_ride 有单测支撑。问题集中在：一个高危账目缺陷、内存态与落库事实不一致、静默失效的功能、时间/数据口径缺陷。

### C-1 【高】模拟盘盈亏缩放污染现金账本：`pnl_base_capital ≠ 100 万` 时每笔盈亏被放大后直接计入现金
`broker/paper_broker.py:524`

任何 `pnl_base_capital ≠ 1,000,000` 的账户（老账户迁移，或用户 reset 成非 100 万本金），**每笔平仓盈亏都被乘以 `100万/base` 记入现金并逐笔复利放大**。用户把本金 reset 成 1 万即可让每笔盈亏 ×100，轻松刷出天文数字收益率 —— 模拟盘数据、净值曲线、**收益排行与积分体系全部失真**；本金 >100 万的账户则亏损被缩小、风险被低估。

**改法**：现金账本必须记真实金额 `new_cash = cash + net_income`；若需「归一化到 100 万」的展示口径，**只在展示层换算，绝不写回 cash/equity**；限制 `/api/paper/reset` 的 initial_capital 取值范围；为存量账户写一次性对账修复脚本。

### C-2 【中】加仓追板层数只存进程内存：实盘重启后归零导致重复加仓
`core/trade_service.py:179`（`_ADD_POSITION_LAYERS`）。盘中重启后层数回到 1.0，若持仓涨幅仍 ≥9%，**会再次以涨停价生成约 17% 仓位的买入信号**（已 executed 的信号不拦截）→ 真金白银重复加仓。模拟盘侧该功能则永远被拒（静默无效），回测与实盘行为不一致。
**改法**：层数落库（`live_positions` 加 layers 列或用当日 executed 信号判断）；加仓前先查当日该 code 的 executed BUY；去掉 `max(...,100)` 强制 1 手。

### C-3 【中】★双维度独立发现★ Vibe 自动交易调度器引用不存在的 `broker.cash` 且把 list 当 dict 遍历
`core/schedulers.py:42,59`（安全/架构两个维度的审查员各自独立发现同一 bug）

所有启用 Vibe 因子自动交易的用户，**每次 tick 都以 `no_cash` 结束，永远不会下单**——功能整体沉默失效且无任何面板报错；同时 `update_daily_pnl` 从未被调用，用户配置的**单日亏损熔断形同虚设**。而 `:112` 传入的是真实下单入口 `execute_buy`（DRY_RUN=False 时走实盘）——一旦有人只修 cash 一处，熔断仍是坏的，构成真实风控缺口。
**改法**：改 `broker._cash()`；按 list 结构遍历 `p["cost_price"]/p["shares"]/p["cur_price"]`；两个 helper 的 except 至少记 warning；补一条 run_tick→下单的最小集成测试。

### C-4 【中】扫描入队 `price = r["price"] or 1`：报价缺失按 1 元算手数并可被自动买入
`strategy_engine/scan_service.py:196`。20 万预算会算出 20 万股；模拟盘以 ≈¥1 成交后成本严重失真（随后显示 +900% 幻影盈亏污染净值），实盘则生成 ¥1 限价买单发往 xiadan，白占当日开仓名额与资金额度。
**改法**：`price<=0` 直接 continue 并记 error，绝不用 1 元兜底；`execute_buy` 再加一道偏离昨收 ±20% 的拒单校验。

### C-5 【中】模拟盘手动买入完全信任前端传入的成交价
`web/paper.py:190`。多用户竞争平台上，用户可用 API 以 ¥0.01「买入」再按市价卖出，**凭空刷出模拟盘利润**，破坏收益统计、排行与积分体系可信度。另 `/api/positions/sell` 用 `DRY_RUN` 而非 `broker_type` 分支，与 execute_buy/execute_sell 口径不一致。
**改法**：成交价以服务端实时行情为准（拉不到就拒单）；偏离涨跌停幅度一律拒绝；分支条件改 `DRY_RUN or broker_type=='paper'`。

### C-6 【中】`is_trading_time` 无 A 股节假日日历且用裸 `datetime.now()`
`market/market_data.py:461`。国庆/春节等落在工作日的休市日**照常派发扫描**：策略基于陈旧行情产生信号，模拟盘以陈旧价「成交」，today_trades/hold_days 全按错误口径累计。若 ECS 时区非 Asia/Shanghai，交易窗口、15:00 收盘终止、隔日信号过期（SQLite localtime）**整体错位**。
**改法**：引入交易日历（tushare trade_cal 或本地假日表）；`_now()` 显式用 `zoneinfo("Asia/Shanghai")`；部署脚本固化时区 + 启动自检断言。

### C-7 【中】全市场回测样本用「当前」实时行情筛选：幸存者偏差 + 前视偏差
`strategy_engine/backtest.py:727`。股票池由「今天仍活跃、价格>3 元」的票组成，剔除了期间退市/仙股化/停牌标的，并用未来信息（当前成交量排名）选样本 → **回测收益系统性虚高**，而用户据此决定是否把策略投入实盘。
**改法**：按回测起始日的历史快照构建股票池；至少在结果页明示偏差；长期落地含退市股的历史股票宇宙表。

### C-8 【中】实盘台账把信号价当成交价：`live_positions` 成本价失真
`web/bridge.py:993`。打板/追高场景信号价与真实成交价可差 1%-3%+，`_check_live_daban_ride` 与止损止盈按错误成本算 pnl（`trade_service.py:315,339`）→ **提前止盈、延迟止损**，加权均价随每笔偏差累积漂移。
**改法**：桥接器回报 executed 时携带真实成交均价（今日委托页 OCR 已有该数据），report 接口落库 `exec_price`；取不到时标记 `price_source='signal'` 供风控降级。

### C-9 【低】实盘手动卖出依赖易失的内存持仓视图
`core/trade_service.py:169`。服务重启后（云端 systemd 更新即触发）实盘用户点「卖出」一律得到「无持仓」，**行情急跌时人工止损通道被阻断**。
**改法**：实盘分支优先查 `um.get_live_positions(uid)`，内存视图仅作展示缓存。

### C-10 【低】模拟盘涨停/跌停成交仍叠加滑点，成交价越出合法价带
`broker/paper_broker.py:371`。A 股不可能以高于涨停价成交；打板策略每笔成本被高估（3bp 级），高频打板统计产生系统性偏差。
**改法**：封板/跌停路径直接取涨跌停价，或把 exec_price clamp 到 `[limit_down, limit_up]`。

### C-11 【低】内存持仓视图与撮合事实不一致
`core/trade_service.py:117`。手动买 150 股实际成交 100 股时，面板按 150 股显示（虚增 50%）直到重启；`/api/positions/close` **只删内存**，DB 里仓位仍在、风控仍会触发自动卖出，重启后「复活」。

### C-12 【低】`db_migration._safe_add_column` 吞掉所有异常
`core/db_migration.py:33`。`database is locked` 等失败被当作「列已存在」静默跳过 → `today_trades` 无法持久化 → **重启当天日内开仓限额失效可超限开仓**；max_positions/单笔上限回退 config 默认，护栏被悄悄放松。
**改法**：except 里用 `PRAGMA table_info` 复查列是否真存在；护栏相关列失败应阻断启动。
